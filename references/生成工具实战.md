# 生成工具实战

分镜表写得再好，落到提示词上错了句法，出来的东西也不对。这份文件解决「怎么写才生效」。

> 综合自 `jnMetaCode/ai-shortfilm-prompts` 开源方法论（Mx-Shell《丧尸清道夫》提示词体系）、主流平台的运镜提示词实测经验，以及本 skill 的 MV 专用约定。平台行为随版本变化，模型差异部分请按当前版本重新验证。

---

## 一、六模块句法

一句话拆成六块，顺序固定：

```
[镜头运动] + [速度/幅度] + [画面主体及其动作] + [场景环境] + [光线氛围] + [画质风格]
```

前三个模块不要省。

**镜头运动放句首。** 模型的注意力对句首权重更高，运镜是整段的骨架，骨架必须靠前。埋在长句中间的运镜指令，大概率不生效。

范本：

```
Camera slowly dollies in toward a girl standing by the window, she turns her head and settles, morning light through the glass, dust floating in the air, 35mm film look
```

中文：

```
镜头缓慢推近窗边的女孩，她转头后停住，晨光透过玻璃洒落，空气中漂浮着尘埃颗粒，35mm 胶片质感
```

## 二、三条最容易翻车的句法规则

### 规则 1：主体运动和镜头运动必须分开写

这是最高频的翻车点。写「镜头推向奔跑的人」，模型会把两个动词融合成一种奇怪的混合运动——人物原地跑、背景不动，或者画面跟着人剧烈晃。

**做法**：分两句写，用逗号或句号隔开。

```
✗ dolly in and man running
✓ Camera dollies in. A man runs from left to right across the street, the camera follows his movement smoothly.
```

两个动作各自定义清楚，再用 while / as / and 组合。

### 规则 2：写清起幅和落幅的景别

只写「推近」，模型不知道从哪推到哪，中间容易变形或跳跃。

**做法**：补 `from wide shot to close-up`。

```
Camera slowly pushes in from a wide shot to a close-up of the old man's face
```

### 规则 3：用「camera + 动词」消歧义

`pan` 单独出现时，模型经常理解成「画面平移」或「主体横移」，而不是「机位不动、镜头转头」。

**做法**：写 `camera pan`，并补 `camera stays in place`。

```
Camera pans right across the shoreline, camera stays in place, golden dusk light
```

同理，需要完全静止的镜头，正面写 `static camera, fixed shot, no camera movement`，负面再补 `dynamic camera, camera shake, motion blur`。

## 三、运镜词的精确选择

| 想要的效果 | 写这个 | 不要写 | 原因 |
|---|---|---|---|
| 机位物理靠近 | `dolly in` / `push in` | `zoom in` | dolly 有真实透视变化，背景后退自然 |
| 焦距拉近 | `zoom in` | `dolly in` | zoom 有背景压缩感，冲击力强但假 |
| 机位不动、镜头转 | `camera pan / tilt, camera stays in place` | `pan` | 单独 pan 会歧义 |
| 与主体同速横移 | `trucking right alongside X, both moving at the same speed` | `tracking shot` | 要明确「同速」，否则模型把两者绑定或解绑 |
| 主体静止、镜头移动 | 额外补 `subject stays still` | — | 不写，模型倾向让主体跟着动 |
| 环绕 | `slight orbit` / `orbits from left to right` | `360 degree orbit` | 角度越大越容易脸崩、透视扭曲 |
| 升降 | `crane up / crane down`，写明起幅与落幅 | `rise up` | 不写落幅，模型中途自由发挥 |
| 甩镜 | `fast whip pan` | `quick pan` | whip pan 会带动态模糊，能当转场用 |
| 希区柯克变焦 | `dolly in while zoom out, vertigo effect` | — | 成功率不稳，多抽几次 |

**环绕的角度上限**：MV 里建议 ≤ 60–90°。原案例 S08 用「orbit 约 60°」，S14 用「围绕罐子极缓 orbit」，都是小角度。大幅环绕在抒情片里显得炫技，而且容易崩脸。

## 四、三个反直觉的写法

来自 Mx-Shell 体系，和「写得更美」正好相反——它们靠**具体**取胜，不靠形容词。

### 1. 指定真实摄影机与镜头型号

不要写 `cinematic feel`（电影感）。这是最空的词，模型无法锚定。

写：

```
simulated IMAX film camera, Panavision C-series lens, 35mm focal, f/4 aperture
```

原理：训练数据里这些具体字符串和高品质影像强绑定，而「电影感」这个词什么都绑。

MV 的二维动画场景可以这样用：

```
模拟 35mm 电影镜头质感，f/4 浅景深，轻微胶片颗粒
```

### 2. 描述瑕疵

完美看起来假。真实感来自缺陷。

```
✓ 战损装甲，掉漆，关节油污，保留面部小瑕疵
✓ 毛衣起球，袖口磨白，玻璃罐身有一处磕碰缺口
```

这条对 MV 极有用：**核心道具的「一处永久瑕疵」是防止跨镜换道具的最强锚点**，同时也是质感的来源。

### 3. 留空结尾

不要让每镜都以「高潮」收尾。

```
✗ 结尾：她泪流满面，光芒大盛
✓ 结尾：没有对白，没有爆闪。只是她站在那里，远处一颗火星落下
```

「留空」= 给下一镜留接口，也给观众留呼吸。

## 五、平台差异（会随版本变化，用前先验）

据 `ai-shortfilm-prompts` 的实测记录：

| 平台 | 关键特性 | 应对 |
|---|---|---|
| **Runway Gen-4** | **不支持负面提示词**。写 `no distorted hands` 反而可能召唤出扭曲的手 | 只能正向描述。这是移植提示词最大的坑 |
| **Veo 3 / 3.1** | 负面词字段只要**名词短语**，不要 `no` / `don't` 命令式 | 写 `rain, watermark`，不写 `no rain` |
| **Kling（可灵）** | 有预生成违禁词过滤器，**命中一处整条提示词被拒** | 先净化用词，准备一版「安全词替换」 |
| **Sora 2** | 过滤的是**描述本身**而非专名 | 写「橙衣尖发忍者」一样会被拦，改写描述 |
| **通用** | 中文模型对中文运镜词响应更好；英文模型对英文术语更敏感 | 不要中英混输，二选一 |

**WorkBuddy 内置的生图 / 图生视频能力**遵循通用规律，上面第一到第四节全部适用；平台差异部分主要针对外部工具。

**结论**：负面提示词库不能无脑粘贴。用之前先确认目标平台是否支持负面字段。

### 本机实测（2026-10-23，以 WorkBuddy 内置能力为准）

不要凭记忆假设「内置能力是什么模型」——它会变。跑之前先确认一次，最省事的办法是故意传一个不支持的分辨率（如 `480P`），返回里的 warning 会直接把模型名念出来：`resolution 480P is not supported by model kling-video-v3`。

当前实测参数（服务端下发，模型清单在 `~/.workbuddy-ai/cache/acc-product-config-v3.json`）：

| 项 | 实测值 | 对 MV 制作的含义 |
|---|---|---|
| 视频模型 | `kling-video-v3`（可灵 V3），**只有一个** | 没有模型可选，不用纠结选型；风格全靠提示词锚 |
| 分辨率 | 720P / 1080P / 4K，**无 480P** | 传 480P 会被静默降级成 720P。要试错就用 720P，别指望 480P 省钱 |
| 时长 | 3–15 秒，默认 5 | 一句歌词 3–4 秒刚好落在下限附近，**不要再按「5 秒一段」写分镜** |
| 画幅 | 16:9 / 9:16 / 1:1（仅文生视频） | 图生视频的画幅由首帧决定，所以首帧必须先按 16:9 出好 |
| 音轨 | `switchable`，默认**开** | 必须显式关掉。否则每段都带模型自己编的环境音，后期套歌时全部要拆 |
| 首尾帧 | 支持，但 `lastFrameRequiresFirstFrame: true` | 想锁尾帧就必须同时给首帧。**这正是「上一镜尾帧 → 下一镜首帧」的落地接口** |
| 参考图 | `maxReferenceImages: 0`，**不支持** | 不能用多图参考锁角色。角色一致性只能靠「首帧继承 + 风格锚逐字复制」 |
| 负面提示词 | 有独立字段，2500 字符 | 负面提示词库可以整段粘，不受 Runway 那种限制 |
| 水印 | 左上角固定「AI生成」 | 成片要裁边或用 ffmpeg `delogo` 处理，**这个在分镜阶段就要预留安全区** |

实测出的两条注意：

1. **不写风格锚 = 出写实片**。同一句「退潮后的海边浅滩，镜面湿沙」，不加风格锚时出来的是写实电影感实拍，不是二维手绘。风格锚不是「锦上添花」，是决定片种的开关。
2. **`seconds` 给到下限附近更安全**。15 秒上限看起来宽松，但一段 15 秒的镜头里模型会自己加戏，与「一句一镜」的卡点原则冲突。

### 图生视频的三条硬规律（2026-10 实测，7 条素材、重跑率 43%）

图生视频不是「让首帧动起来」，它是一次**以首帧为条件的重绘**。理解这一点，很多失败就能提前避开。

**规律一：它只会加细节，不会减细节。**

首帧里含混的东西会被逐帧「补全」。所以：

- 想要虚化的轮廓 → 关键帧里不能有轮廓，只能有光斑或雾团
- 想要模糊的背影 → 关键帧里就得是失焦的色块，不能是清晰剪影再指望它变糊
- 想要「看不清五官」的脸 → 关键帧里干脆不要脸

一句话：**虚化不是运动效果，是首帧属性。** 凡是「我希望它保持不清晰」的元素，都必须在不清晰的状态下被画出来。

**规律二：小物件会被当成噪点抹掉。**

一颗柠檬、一枚硬币、一根发卡，在 4 秒的重绘里很容易消失或被挪位——尤其当它颜色单一、面积小、周围是纹理复杂的背景时。

对策是在视频提示词里单开一段「道具锁定」，四个条件全给：

```
道具锁定：窗台右三分之一处那颗完整柠檬全程留在原处、位置大小不变、
不能被遮挡、不能被拿走、不能消失，它是画面里唯一鲜艳的黄色。
```

最后半句是关键。**给道具一个不可替代的身份**（唯一鲜艳色 / 唯一光源 / 唯一会动的物体），模型才有理由保留它。

**规律三：运镜的落幅要写「景别 + 占比」，不能只写「落幅是什么」。**

写「落幅她的手与柠檬」，会得到手部大特写——因为「手」是最容易成为视觉中心的东西。要写：

```
落幅硬指标：结束时仍是中景，能同时看到她的上半身、裙子和窗框，
她的手与柠檬只占画面下半部三分之一，绝不推成手部特写。
```

内容 + 景别 + 画面占比，三个都给才收得住。只给内容，模型会自己决定景别，而它倾向于越推越近。

### 水印：图像和视频不在同一个角

实测本机两个模型的水印位置不同：

| 来源 | 位置 | 处理时机 |
|---|---|---|
| 图像模型（关键帧） | **右下角**，半透明白字，亮度约 155/255 | 喂进图生视频**之前**必须先补掉 |
| 视频模型（成片） | **左上角**，带圆角框 | 成片阶段用 `delogo` 去掉 |

关键帧水印没去就喂进去，后果不只是「带进视频」——模型会把它当成画面里的真实内容，参与重绘，有时会把它「补」得更清楚。

图像侧补水印用邻域克隆（把水印左侧同高度的区域平移过来，边缘羽化）：

```python
src = im.crop((x0 - 260, y0, x0 - 260 + bw, y0 + bh)).filter(ImageFilter.GaussianBlur(1.2))
mask = 羽化矩形
im.paste(src, (x0, y0), mask)
```

视频侧用 `delogo`：

```bash
ffmpeg -i in.mp4 -vf "delogo=x=6:y=4:w=130:h=66" -c:v libx264 -preset slow -crf 16 -pix_fmt yuv420p -r 24 -an out.mp4
```

`delogo` 在暗部背景上几乎无痕；亮背景会留一圈平滑过渡，此时应改用裁边，或在分镜阶段就把水印区域留给暗部构图。

## 六、参数控制

| 参数 | 建议 | 说明 |
|---|---|---|
| 运动幅度（motion scale，0–10） | **5–7** | 超过 8 画面边缘明显扭曲。要更戏剧化，宁可后期加速，不要拉参数 |
| 时长 | 3–4 秒 | 超过 5 秒后段容易失控（人物变形、动作重复） |
| 种子（seed） | **锁定并记录** | 找到满意版本后立刻记下种子，之后只改单个字段，不要整体重 roll |
| 分辨率 | 先低后高 | 先用低分辨率测提示词是否生效，确认后再渲高分辨率 |

**只改一个变量的原则**：调速度就只改速度副词，调光就只改光，不要同时改三处。否则你不知道是哪个改动起了作用。

## 七、翻车排查表

| 现象 | 可能原因 | 排查方向 |
|---|---|---|
| 画面完全不动 | 运镜词被长句淹没 | 镜头指令挪到句首，单独成句 |
| 运动方向不对 | 动词被误读 | 补近义词，明确「向左/右/前」 |
| 幅度时大时小 | 速度副词不平滑 | 用 gradually / slowly 替换 fast |
| 画面扭曲变形 | 运动幅度过大 | 降参数，改为后期加速 |
| 主体变脸 | 跨镜描述不一致 | 主体描述逐字固定，不换近义词 |
| 多镜衔接跳变 | 镜头间缺过渡信息 | 加 revealing / turning into 等衔接词 |
| 动作像提线木偶 | 缺起势与跟随 | 补预备动作、跟随重叠（见 `动画原理.md`） |
| 人物像蜡像 | 缺次要动作 | 补「轻微呼吸起伏、偶尔眨眼」 |
| 风格漂移 | 风格锚每镜改写 | 风格锚逐字复制，全片零改动 |
| 画面自己加运镜 | 未声明固定机位 | 正面写 static camera，负面补 camera shake |
| 中文提示词没反应 | 平台主语言是英文 | 换英文，或换同义中文描述 |

## 八、提示词记录库

提示词是经验科学，不是公式。同一句话在不同版本、不同平台上效果会变。**必须记录。**

建议每镜存一行：

| 字段 | 例 |
|---|---|
| 镜号 | S07 |
| 平台与版本 | 【】 |
| 提示词全文 | 【完整复制】 |
| 速度副词 | slowly / gently |
| 运动幅度参数 | 6 |
| 种子 | 1234567 |
| 首帧来源 | S06 尾帧 |
| 结果评价 | 可用 / 需重跑 / 最佳 |
| 备注 | 袖口跟随没出来，下次补 follow-through |

批量做同系列 MV 时，这张表能省掉大量重复试错。**「见过的坑足够多、踩过的路有记录」比灵光一现重要。**

## 九、分段生成 vs 一次长生成

**永远选分段。**

理由：

1. 一次生成 15 秒，后 10 秒的质量必然下降（动作重复、人物漂移）
2. 分段可以只重跑坏的那 3 秒，长生成只能整段重来
3. 分段的切点精确可控，长生成只能事后剪

标准做法：每段 3–4 秒，首帧接上一段尾帧，段间允许 2 帧重叠。
